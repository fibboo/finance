# backend

## Primary keys

Every table that owns its `id` generates it in PostgreSQL with `server_default=func.uuidv7(monotonic=True)`. The transaction subtype tables (`transactions_expense`, `transactions_income`, `transactions_transfer`) generate nothing: their `id` is a foreign key to `transactions.id` and is copied from the base row. UUIDv7 keys grow with time, so new rows append to the end of the primary-key index instead of landing at random pages. The `monotonic` flag tells SQLAlchemy that the values grow, which lets it insert a batch of rows in one `INSERT … RETURNING` and match the returned keys to the objects (`CRUDBase.create_batch`).

No `id` is a secret. A refresh token (`app/models/user/refresh_token.py`) is a random string the browser keeps in a cookie, and the table stores only its SHA-256 hash, so a UUIDv7 key revealing when a row was created gives nothing away.

## Tokens

The API authenticates by a short-lived HS256 JWT access token (`app/services/user/token_service.py`). `get_user_id` (`app/api/deps.py`) checks its signature and expiry and returns its `sub` without reading the database, so an access token stays valid until it expires even after its refresh token is revoked.

Refresh tokens rotate: each use revokes the presented token and issues a new one in the same family. Presenting a token that is already revoked means it was copied, so the whole family is revoked (reuse detection). That revocation must outlive the 401 it answers with, while `DbTransaction` rolls a request back on any exception. So `_get_db_transaction` commits before re-raising `RefreshTokenReusedException`, and only that one.

The backend serves web clients only. The refresh token never appears in a response body: `POST /user/auth/token` answers the access token as JSON and sets the refresh token as the `refresh_token` cookie, `HttpOnly; Secure; SameSite=Strict` with `Path=/user/auth` and `Max-Age` of `refresh_token_expire_seconds` (`app/api/cookies.py`, which defines the name and attributes once). The handler calls `auth_service.grant_token`, which picks the grant, and hands the token pair to `cookies.build_token_response`, which sets the cookie and returns the body. The frontend proxy rewrites the path to where it serves the API; the backend knows nothing about that. `Secure` stays on everywhere. Chromium and Firefox treat `http://localhost` as a secure context and accept the cookie there, while Safari may drop it, so local development uses Chrome or Firefox. Both grants of `POST /user/auth/token` and `POST /user/auth/revoke` read the cookie through `get_refresh_token` (`app/api/deps.py`), which also answers 403 `ORIGIN_NOT_ALLOWED` when an `Origin` header is present and not in `allowed_origins`, as a CSRF defence next to `SameSite=Strict`. `allowed_origins` holds the frontend's origin, since the proxy serves the API from it. A refresh grant without the cookie is answered 401 `INVALID_TOKEN` by `auth_service.grant_token`. `/revoke` without the cookie answers 200 and only clears it, since RFC 7009 has a revocation always succeed. The authorization code grant revokes the family of a cookie it is sent before it issues a new family, so a second sign-in in the same browser leaves no live token behind. A refresh grant that fails with an unknown, expired or reused token raises a `RefreshTokenRejectedException`, whose handler in `app/main.py` clears the cookie on the 401. `/revoke` clears the cookie.

## Request transaction

A writing endpoint and every dependency that shares its session take it as `db: DbTransaction` (`app/api/deps.py`), the one declaration of the private `_get_db_transaction` with `scope="function"`. No handler sets the scope itself. A dependency with `yield` in FastAPI's default scope finishes after the response is sent, so the commit would come after the client already saw success: a write that then fails would be reported as done, `/token` would hand out a cookie the database never stored, and the sign-in callback a one-time code whose row is not yet committed. With function scope the transaction commits when the handler returns, before the response goes out, and an exception still passes through the dependency first, so the commit on `RefreshTokenReusedException` keeps working. FastAPI caches a dependency per call and scope, so a session requested with another scope would be a second session in a second transaction; `get_onboarded_user_id` takes `DbTransaction` too and shares the handler's session.

`get_db` gives a plain session for reads and keeps the default scope, since nothing it does has to happen before the response.

## Sign-in

The backend is the OpenID Connect client towards the providers and the authorization server towards our own clients (`app/services/user/auth/auth_service.py`). A client opens `GET /user/auth/authorize/{provider}` with its `redirect_uri`, its own `state` and a PKCE S256 `code_challenge`. These query parameters arrive as one model, `AuthorizeRequest` (`app/schemas/user/authorization_request.py`), which checks them: the method is `S256`, the challenge is 43 base64url characters and the state is 1 to 512 characters. `POST /user/auth/link/{provider}` takes the same model, and the provider callback takes `CallbackRequest`. The handlers pass the models to the service as they are, and the two redirecting handlers declare `response_class=RedirectResponse` with status 307 and return the URL, so no handler builds a response itself and OpenAPI documents a redirect. The `redirect_uri` must be in `allowed_redirect_uris`, since the one-time code is sent there. An `authorization_requests` row keeps our own `state`, `nonce` and provider PKCE verifier next to what the client sent, and the client is redirected to the provider. If the provider's discovery document cannot be fetched, is not JSON or has no `authorization_endpoint`, the call answers 502 `PROVIDER_UNAVAILABLE`.

The provider returns to `GET /user/auth/callback/{provider}`. The code is exchanged and the ID token is checked against the provider's JWKS, `iss`, `aud`, `exp` and `nonce` (`oidc_provider.py`). The user is found by provider and `sub`, or created. A new user takes the provider's username, or `<provider>_<sub>` (the provider in lowercase) when the provider sends none or the username belongs to another user. `users.username` holds 64 characters, so a `sub` longer than 32 characters is replaced there by the first 32 hex characters of its SHA-256, which is still the same for the same identity. The provider's username is also replaced there by the fallback when it is shorter than 3 or longer than 64 characters. `external_users.username` keeps the provider's own username, and the fallback only when the provider sends none. A claim of the wrong type is dropped, as is a `picture` the `users.avatar` column cannot hold (3 to 2560 characters), so the user is created without it; an ID token without a string `sub` redirects with `server_error`. The row gets the hash of a one-time code that lives one minute. An unknown, expired or already completed `state` answers 401, because there is no trusted client to redirect to. A provider error, a failed code exchange, a discovery document, token response or JWKS that is not JSON, a token response without an ID token, a discovery document without `issuer` or `jwks_uri`, a rejected ID token or a new user for whom both usernames are taken redirects to the client with `error` (`server_error` for all but the provider's own error, `invalid_request` for a callback without a code) and marks the row used, so its `state` cannot be completed later, and writes nothing else. The one exception is the race on the unique constraints described below, whose transaction is rolled back, so the row stays unused until it expires 10 minutes after it was created. The callback's `state` is bounded in length. A provider `error` outside the RFC 6749 error characters or longer than 128 characters is replaced by `invalid_request` before it goes into the redirect. `POST /user/auth/token` with `grant_type=authorization_code` accepts the code once, for the same `redirect_uri`, with the verifier matching the stored challenge. An unknown, used or expired code answers 401 `INVALID_TOKEN` alike, as RFC 6749 names all of them `invalid_grant`.

Each call builds a fresh Authlib client, so the discovery document and the JWKS are fetched per request instead of cached in the process. A provider is one entry in `providers.py`: Telegram and Google. Each entry reads its discovery URL from `server_metadata_url` of its settings. In production it is the real provider's; locally both point at one issuer each (`/telegram`, `/google`) of the `mock-oidc` compose service, whose sign-in form accepts any username as the `sub` and any extra claims, so a local sign-in needs no real client (README, Signing in locally). Its tokens carry the host they were requested on as `iss`, so the browser and the backend container both reach it as `mock-oidc.localhost:8080`: browsers resolve `*.localhost` to the local machine, and inside compose the name is a network alias of the service. Its claims are read by their standard OIDC names, and `email` is kept only when `email_verified` is true. The ID token's `iss` must equal the discovery document's `issuer` or one of the entry's `issuer_aliases`: Google issues tokens with `accounts.google.com` as well as `https://accounts.google.com`. Users are matched by provider and `sub`; Telegram's `sub` is not the Telegram user id, which is the separate `id` claim.

A signed-in user links another provider with `POST /user/auth/link/{provider}`. It takes the same client parameters as authorize and the Bearer token, and answers the provider URL as JSON, because a browser redirect cannot carry the Bearer header. A user has at most one identity per provider, so a provider already linked answers 409 `PROVIDER_ALREADY_LINKED`. The request row keeps `link_user_id`. Its callback never attaches the identity itself, since the browser that reaches it is not proven to be the signed-in client: a forged link could otherwise attach an attacker's identity to the victim. Like sign-in, it stores the verified identity on the row (`link_identity`) with the hash of a one-time code and redirects to the client with that code. The client finishes with `POST /user/auth/link/{provider}/complete`, sending the code, its `redirect_uri` and the PKCE `code_verifier` with its Bearer token. The code is checked exactly as at the token endpoint, and it must belong to a link request of the Bearer user for that provider. Only then is it marked used, its `link_identity` cleared and the identity attached. A link code is never accepted by `POST /user/auth/token`. An identity that belongs to another user is never moved. The callback redirects with `error=IDENTITY_LINKED_TO_ANOTHER_USER` and marks the row used, so its `state` cannot be replayed, and writes nothing else. One that already belongs to the same user is a success. Completion checks both rules again, because time passes between callback and completion, and answers 409 `IDENTITY_LINKED_TO_ANOTHER_USER` or `PROVIDER_ALREADY_LINKED`. The unique constraints on `external_users` (`provider, external_id` and `user_id, provider`) close the remaining race: their violations map to the same two errors (`user_service.add_external_user`). On the sign-in callback a violation rolls the request back, the row's `used` mark included, and redirects to the client with `error=server_error` through `ClientRedirect` (`app/exceptions/temporary_redirect_307.py`). It carries the log message, logger and level of the violation it replaces, and its handler in `app/main.py` logs that entry once and answers the redirect. Accounts are never merged by email, because Telegram returns none. `DELETE /user/auth/link/{provider}` removes the identity, locking the user's identities first so that two concurrent calls cannot remove the last one, which answers 409 `LAST_IDENTITY_UNLINK_FORBIDDEN`.

## Base currency

A user is created without a base currency (`users.base_currency` is nullable), so that signing in needs nothing but the provider's answer. The client chooses it once afterwards with `PUT /user/me/base_currency` (`user_service.set_base_currency`), which also creates one account named "Wallet" in that currency with rate 1 (`account_service.create_default_account`) and the standard expense categories with their types (`category_service.create_default_categories`, listed in its `DEFAULT_CATEGORIES`), which the user can rename, delete or add to. It cannot be changed: a second call with another currency answers 409 `BASE_CURRENCY_ALREADY_SET`, because every stored `base_currency_amount` is in that currency. The update only matches a row whose currency is still null, so two concurrent calls cannot both create the Wallet account. A repeated call with the stored currency returns the user unchanged, so a client can retry it safely. Until it is set, `user_service.get_user_base_currency` answers 409 `BASE_CURRENCY_NOT_SET`, which tells the client to show onboarding. The client learns it up front from `GET /user/me` (`user_service.get_user`), which works before onboarding and returns `base_currency` as null until it is set. Reads keep working, but creating an account, category, location, income source or transaction is refused with that 409: the create endpoints take the user id from `get_onboarded_user_id` (`app/api/deps.py`), which asks `get_user_base_currency` first; the account create endpoint takes the base currency itself from `get_base_currency`, which asks the same, since the new account's rate depends on it. So a user has no accounts or categories until the base currency is set, and the Wallet account and the standard categories it creates cannot collide with an existing name.

## Currencies

Currencies live in the `currencies` table (`app/models/accounting/currency.py`), which belongs to no user. Its primary key is the ISO 4217 code and it holds the display name, so it is the one table whose key is not a UUIDv7. The initial revision inserts the supported currencies (USD, EUR, RSD, GEL, TRY and RUB); adding or removing one is left to a future admin. `GET /dictionaries/accounting` (`dictionary_service.get_accounting_dictionaries`) is the one dictionary endpoint of the accounting domain (`.claude/rules/common.md` **Architecture**): it returns the currencies ordered by code as key and label pairs, and later value sets of the domain are added to the same response. Every currency field references the table by code: `users.base_currency`, `accounts.currency` and the `source_currency` and `destination_currency` of a transaction are foreign keys to `currencies.code`, and the schemas take them as `CurrencyCode`, a three-letter string. The OpenAPI schema therefore lists no values, and the client reads them from the dictionary. The service checks a code before it writes it (`currency_service.get_currency`), so an unknown one answers 404 `ENTITY_NOT_FOUND` instead of a foreign key violation: when the base currency is set, when an account is created, and for both currencies of every transaction in the base processor's `create`. The test schema is built from the models' metadata, so the `engine` fixture in `tests/conftest.py` inserts the same currency rows the initial revision does.

## Category types

Every category has a required type that classifies the spending it holds: VARIABLE (recurring, with an amount that changes, such as groceries or transport), FIXED (recurring with about the same amount, such as rent, utilities or subscriptions) and PERIODIC (less often than monthly, often large but predictable, such as travel, devices or gifts). These are the three expense groups of budgeting, and future budgets and reports group by them. `CategoryType` and its labels, `CATEGORY_TYPE_LABELS`, live together in `app/schemas/accounting/category.py`; `GET /dictionaries/accounting` serves them as `category_types` in the enum's order, and the category list filters by `types`.

## Deleted accounts

Every delete in the API is a soft delete and answers 200 with the deleted object, its status DELETED, so the client can update its cache and offer an undo without another request. Transactions, accounts and categories follow it.

Deleting an account is a soft delete: `account_service.delete_account` sets its status to DELETED and returns the account, and only an account with a zero balance can be deleted. Account names are unique among a user's active accounts only. `account_unique_user_id_name` (`app/models/accounting/account.py`) is a partial unique index over the rows whose status is ACTIVE, so a deleted account frees its name for create and update, while two active accounts still cannot share one. The index keeps the name of the former constraint, so a violation still answers 409 `INTEGRITY_ERROR` through `IntegrityException` with the same log message.

`POST /accounting/accounts/{account_id}/restore` (`account_service.restore_account`) turns a deleted account back into an active one. It locks the user's account with that id and status DELETED, as `delete_account` locks an active one, so an unknown or already active account answers 404 `ENTITY_NOT_FOUND`. A deleted account always has a zero balance, so restoring changes only the status. When an active account already holds the name, the partial index refuses the restore with 409 `INTEGRITY_ERROR`, and the user renames the active account first.

A transaction that touches a deleted account can be neither created nor deleted until the account is restored: both would change the balance of an account the user cannot see. The two account validations of the base processor (`app/services/accounting/transaction_processor/base.py`) answer 403 `DELETED_ACCOUNT_TRANSACTION_FORBIDDEN` on creation, which covers all three types and both sides of a transfer. `delete` asks the subclass for the accounts the transaction references (`_get_transaction_accounts`) and refuses before it marks the transaction deleted. A future transaction edit follows the same rule.

## Deleted categories

`DELETE /accounting/categories/{category_id}` (`category_service.delete_category`) is a soft delete, like an account's: it locks the user's active category with that id, sets its status to DELETED and returns it, so an unknown or already deleted category answers 404 `ENTITY_NOT_FOUND`. The list, `get_category` and `update_category` see active categories only. The expense processor checks the category through `get_category`, so an expense with a deleted category answers 404, while the expenses that already reference it keep it and still return it. Category names are unique among a user's active categories only: `category_unique_user_id_name` (`app/models/accounting/category.py`) is a partial unique index over the ACTIVE rows that keeps the name of the former constraint, so a deleted category frees its name and a violation still answers 409 `INTEGRITY_ERROR`. A deleted category cannot be restored.

## Transaction amounts

Every transaction (`app/models/accounting/transaction.py`) stores the money it moves in five fields:

- `source_amount`: the amount in the withdrawal currency
- `source_currency`: the withdrawal currency
- `destination_amount`: the amount in the receiving currency
- `destination_currency`: the receiving currency
- `base_currency_amount`: the amount in the user's base currency

What source and destination mean depends on the transaction type:

- **Expense**: `source_*` is the amount withdrawn from the account, and `destination_*` is the amount in the seller's or recipient's currency.
- **Income**: `source_*` is the incoming amount in its original currency, which may be any currency, and `destination_*` is the amount credited to the receiving account. When `destination_currency` is the base currency, `base_currency_amount` is `destination_amount`, the amount credited; otherwise, when `source_currency` is, it is `source_amount`. A request that sends `base_currency_amount` in either case answers 422 `BASE_CURRENCY_AMOUNT_NOT_ALLOWED`, even with the derived value, as an adjustment does. When neither currency is the base one, the request carries `base_currency_amount`, and an income without it answers 422 `BASE_CURRENCY_AMOUNT_REQUIRED`.
- **Transfer**: `source_*` is the withdrawal from one account, and `destination_*` is the deposit to the other account, which must be a different account. When both currencies are the same, `destination_amount` may be omitted and is set to `source_amount`; a different value answers 422 `TRANSFER_AMOUNT_MISMATCH`. A transfer into the base currency from another one derives `destination_amount` as `source_amount` over the source account's rate, and a request that sends `destination_amount` answers 422 `DESTINATION_AMOUNT_NOT_ALLOWED`, even with the derived value. Such a transfer outside the base currency takes its base currency amount from the source account's rate, so the receiving account needs no rate of its own: when it has none, it takes the source account's rate. A transfer between two other currencies that differ takes its base currency amount the same way, and a receiving account without a rate takes the transaction's own rate (`destination_amount / base_currency_amount`), as after any first credit.
- **Adjustment**: `source_*` and `destination_*` are both the difference between the new and the old balance, in the account currency.

An account's `base_currency_rate` is how many units of its currency one unit of the base currency buys, so its balance in the base currency is `balance / base_currency_rate`. An account in the base currency always has rate 1, a rule held by one pure calculator, `utils.get_fixed_base_currency_rate`: it is created with it (`account_service.create_account`, which gets the base currency from the `get_base_currency` dependency, and the Wallet account), and every recalculation below keeps it, so a debit from it is never refused for a missing rate. Every rate is rounded to 10 decimal places in one place, `_quantize_rate`: a rate is small whenever the account currency is the stronger one (1 RSD is about 0.0085 EUR), and 4 places would keep one or two significant digits of it, or round it to 0, which means no rate. The `accounts.base_currency_rate` column is an unscaled `Numeric`, so only this rounding sets the precision. Every base currency amount a processor derives through a rate (an expense, a transfer from another currency, an adjustment of an account with a known rate) is rounded to cents in one place as well, `_quantize_amount`, and kept at 0.01 at least: an amount must be positive, and a small amount in a currency much weaker than the base one would otherwise round to 0.00 and fail validation. Balances are rounded to cents without that minimum, since a balance may be 0 or negative. A debit (expense, the source of a transfer) keeps the rate, even when it empties the account, so an overdraft and a transfer into the account go on working. The reversal of a debit when it is deleted keeps it too, except on an account outside the base currency that has no rate (rate 0, for instance after the deletion of an income emptied it) and gets money back: it then takes the rate a first credit would, `_get_first_rate` of the transaction (`source_amount / base_currency_amount`), so that no account holds money without a rate (`__get_debit_rate`). `delete` loads the base currency for this, as `create` does. A credit (income, the destination of a transfer) and the reversal of one when it is deleted take the rate from one pure calculator, the base processor's `__get_credit_rate`: 1 for a base currency account, 0 when the balance of another one becomes 0, the transaction's own rate (`_get_first_credit_rate`: `_get_first_rate` of `destination_amount / base_currency_amount`, or the source account's rate for a transfer within one currency, which `transfer.py` overrides) when the account has no rate yet or when the balance crosses from zero or below to above zero, the weighted average `new_balance / new_base_balance` when the balance stays positive and so does its base value, and the existing rate in every other case: a balance that stays negative, or a base value that would reach zero or below, which would divide by zero or give a negative rate.

## Balance adjustments

An ADJUSTMENT transaction (`transaction_processor/adjustment.py`) sets an account to the balance the user enters: the starting balance after onboarding, or the real one when the account drifts from the bank. The request carries `account_id` and `new_balance`, not amounts; the processor locks the account, computes the difference and stores it as both amounts. Amounts are positive, so the direction is the side: `transactions_adjustment` has a nullable `from_account_id` and `to_account_id`, a check constraint keeps exactly one of them set, and an increase fills `to_account_id` while a decrease fills `from_account_id`. An adjustment never changes a rate the account already has. Its base currency amount is derived from that rate, so letting the base credit recompute the rate from the rounded amount would only feed rounding back into it: a cent correction on a small balance would move the rate far, and an increase that takes a negative balance just above zero could divide by zero. So the adjustment has its own `_update_from_account` and `_update_to_account`, which move the balance through the base deltas (`_get_from_account_delta`, `_get_to_account_delta`) and keep the existing rate while the balance stays non-zero. An account whose balance is 0 counts as having no rate, even when it still carries one (`__has_known_rate`; the account still shows that rate through the API, but the adjustment does not use it): a debit that empties an account keeps its rate so that an overdraft and a transfer into it go on working, but that rate belongs to money that is gone. A base currency account keeps rate 1 throughout. So an adjustment of an empty or rateless account outside the base currency sets the rate a first credit would, `_get_first_rate` (`destination_amount / base_currency_amount`), and the rate of such an account becomes 0 when the balance does. That last case also covers a decrease of an empty account below zero, such as the starting balance of a credit card, which would otherwise leave a debt without a rate that no expense could debit. Deleting an adjustment moves the balance back the same way, and the rate of an account outside the base currency returns to 0 when the balance does. A new balance equal to the current one answers 422 `ACCOUNT_BALANCE_UNCHANGED`. `base_currency_amount` is the difference itself for a base currency account and the difference divided by the account rate when the account has a known rate (a non-zero balance and a non-zero rate), rounded by `_quantize_amount`, so that a correction of a fraction of a cent still makes a positive amount; an account outside the base currency without a known rate takes it from the request, and answers 403 `NO_ACCOUNT_BASE_CURRENCY_RATE` without it. A request that sends `base_currency_amount` for an account whose rate is known, because it is in the base currency or already has one, answers 422 `BASE_CURRENCY_AMOUNT_NOT_ALLOWED` instead of having the value silently ignored. The not-found and deleted-account checks are the base processor's `_validate_account_is_active`, shared by the adjustment and the account validations of the other types. The currencies of an adjustment are the locked account's, so `create` checks no currency for it (`_get_request_currencies`), while the other types check the distinct currencies of the request before the processor reads any account. Adjustments are neither income nor expense: reports that sum incomes and expenses read only those two types. An adjustment is deleted like any other transaction, which moves the balance back.

## Summary

An account's balance in the base currency is computed in one place, `utils.get_base_currency_balance`: `balance / base_currency_rate` rounded to cents, and 0 while the account has no rate. The account response exposes it as the computed `base_currency_balance`, and `GET /accounting/summary` (`summary_service.get_summary`) sums the same rounded values of the user's active accounts as `total_balance`, so the total always equals the sum of the balances the client shows. The summary takes `month`, any date inside the month and today's month by default, and answers its first day. The backend works in UTC throughout, so that default is the UTC date; time zones belong to the frontend, which sends `month` when the user's local month differs. Earned and spent are the sums of `base_currency_amount` of the active income and expense transactions dated inside the month, read in one aggregate query; left over is their difference and may be negative.

## Migrations

The application is deployed, and the production database is stamped with the revisions in `db_migration/versions/`. So every schema change adds a new revision on top with `alembic revision --autogenerate`; an existing revision is never edited, deleted or regenerated, since the production database could no longer find it and `alembic upgrade head`, which every deploy runs before the new backend starts, would fail. The previous backend keeps serving on the new schema until the new one replaces it, so a revision that drops or renames a column, or adds a `NOT NULL` column without a default, ships in two deploys: first the code that no longer uses the old shape, then the revision.
