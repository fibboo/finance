# backend

## Primary keys

Every table that owns its `id` generates it in PostgreSQL with `server_default=func.uuidv7(monotonic=True)`. UUIDv7 keys grow with time, so new rows append to the end of the primary-key index instead of landing at random pages. The `monotonic` flag tells SQLAlchemy that the values grow, which lets it insert a batch of rows in one `INSERT … RETURNING` and match the returned keys to the objects (`CRUDBase.create_batch`).

No `id` is a secret. A refresh token (`app/models/user/refresh_token.py`) is a random string the browser keeps in a cookie, and the table stores only its SHA-256 hash, so a UUIDv7 key revealing when a row was created gives nothing away.

## Tokens

The API authenticates by a short-lived HS256 JWT access token (`app/services/user/token_service.py`). `get_user_id` (`app/api/deps.py`) checks its signature and expiry and returns its `sub` without reading the database, so an access token stays valid until it expires even after its refresh token is revoked.

Refresh tokens rotate: each use revokes the presented token and issues a new one in the same family. Presenting a token that is already revoked means it was copied, so the whole family is revoked (reuse detection). That revocation must outlive the 401 it answers with, while `DbTransaction` rolls a request back on any exception. So `_get_db_transaction` commits before re-raising `RefreshTokenReusedException`, and only that one.

The backend serves web clients only. The refresh token never appears in a response body: `POST /user/auth/token` answers the access token as JSON and sets the refresh token as the `refresh_token` cookie, `HttpOnly; Secure; SameSite=Strict` with `Path=/user/auth` and `Max-Age` of `refresh_token_expire_seconds` (`app/api/cookies.py`, which defines the name and attributes once). The handler calls `auth_service.grant_token`, which picks the grant, and hands the token pair to `cookies.build_token_response`, which sets the cookie and returns the body. The frontend proxy rewrites the path to where it serves the API; the backend knows nothing about that. `Secure` stays on everywhere. Chromium and Firefox treat `http://localhost` as a secure context and accept the cookie there, while Safari may drop it, so local development uses Chrome or Firefox. Both grants of `POST /user/auth/token` and `POST /user/auth/revoke` read the cookie through `get_refresh_token` (`app/api/deps.py`), which also answers 403 `ORIGIN_NOT_ALLOWED` when an `Origin` header is present and not in `allowed_origins`, as a CSRF defence next to `SameSite=Strict`. `allowed_origins` holds the frontend's origin, since the proxy serves the API from it. A refresh grant without the cookie is answered 401 `INVALID_TOKEN` by `auth_service.grant_token`. `/revoke` without the cookie answers 200 and only clears it, since RFC 7009 has a revocation always succeed. The authorization code grant revokes the family of a cookie it is sent before it issues a new family, so a second sign-in in the same browser leaves no live token behind. A refresh grant that fails with an unknown, expired or reused token raises a `RefreshTokenRejectedException`, whose handler in `app/main.py` clears the cookie on the 401. `/revoke` clears the cookie.

## Request transaction

A writing endpoint and every dependency that shares its session take it as `db: DbTransaction` (`app/api/deps.py`), the one declaration of the private `_get_db_transaction` with `scope="function"`. No handler sets the scope itself. A dependency with `yield` in FastAPI's default scope finishes after the response is sent, so the commit would come after the client already saw success: a write that then fails would be reported as done, `/token` would hand out a cookie the database never stored, and the sign-in callback a one-time code whose row is not yet committed. With function scope the transaction commits when the handler returns, before the response goes out, and an exception still passes through the dependency first, so the commit on `RefreshTokenReusedException` keeps working. FastAPI caches a dependency per call and scope, so a session requested with another scope would be a second session in a second transaction; `get_onboarded_user_id` takes `DbTransaction` too and shares the handler's session.

`get_db` gives a plain session for reads and keeps the default scope, since nothing it does has to happen before the response.

## Sign-in

The backend is the OpenID Connect client towards the providers and the authorization server towards our own clients (`app/services/user/auth/auth_service.py`). A client opens `GET /user/auth/authorize/{provider}` with its `redirect_uri`, its own `state` and a PKCE S256 `code_challenge`. These query parameters arrive as one model, `AuthorizeRequest` (`app/schemas/user/authorization_request.py`), which checks them: the method is `S256`, the challenge is 43 base64url characters and the state is 1 to 512 characters. `POST /user/auth/link/{provider}` takes the same model, and the provider callback takes `CallbackRequest`. The handlers pass the models to the service as they are, and the two redirecting handlers declare `response_class=RedirectResponse` with status 307 and return the URL, so no handler builds a response itself and OpenAPI documents a redirect. The `redirect_uri` must be in `allowed_redirect_uris`, since the one-time code is sent there. An `authorization_requests` row keeps our own `state`, `nonce` and provider PKCE verifier next to what the client sent, and the client is redirected to the provider. If the provider's discovery document cannot be fetched, is not JSON or has no `authorization_endpoint`, the call answers 502 `PROVIDER_UNAVAILABLE`.

The provider returns to `GET /user/auth/callback/{provider}`. The code is exchanged and the ID token is checked against the provider's JWKS, `iss`, `aud`, `exp` and `nonce` (`oidc_provider.py`). The user is found by provider and `sub`, or created. A new user takes the provider's username, or a fallback when the provider sends none, the username belongs to another user in any case (`user_crud.get_user_by_username` compares `lower(username)`, which the unique index serves), or it is shorter than 3 or longer than 64 characters (what `users.username` holds). The fallback is `user_` followed by 8 random lowercase letters and digits (`user_service.FALLBACK_USERNAME_*`), so it never shows the provider's id and cannot be taken in advance for a given identity; a fallback that is already taken is generated again, up to 5 times. `external_users.username` keeps the provider's own username, and the user's fallback only when the provider sends none; a linked identity without a username gets a fallback of its own. A claim of the wrong type is dropped, as is a `picture` the `users.avatar` column cannot hold (3 to 2560 characters), so the user is created without it; an ID token without a string `sub` redirects with `server_error`. The row gets the hash of a one-time code that lives one minute. An unknown `state` answers 401, because there is no trusted client to redirect to. An expired or already completed one redirects to the client redirect URI stored on its row with `error=expired_request` through `ClientRedirect` and writes nothing. A provider error, a failed code exchange, a discovery document, token response or JWKS that is not JSON, a token response without an ID token, a discovery document without `issuer` or `jwks_uri`, a rejected ID token or a new user for whom the provider username and every fallback are taken redirects to the client with `error` (`server_error` for all but the provider's own error, `invalid_request` for a callback without a code) and marks the row used, so its `state` cannot be completed later, and writes nothing else. The one exception is the race on the unique constraints described below, whose transaction is rolled back, so the row stays unused until it expires 10 minutes after it was created. The callback's `state` is bounded in length. A provider `error` outside the RFC 6749 error characters or longer than 128 characters is replaced by `invalid_request` before it goes into the redirect. `POST /user/auth/token` with `grant_type=authorization_code` accepts the code once, for the same `redirect_uri`, with the verifier matching the stored challenge. An unknown, used or expired code answers 401 `INVALID_TOKEN` alike, as RFC 6749 names all of them `invalid_grant`.

Each call builds a fresh Authlib client, so the discovery document and the JWKS are fetched per request instead of cached in the process. A provider is one entry in `providers.py`: Telegram and Google. Each entry reads its discovery URL from `server_metadata_url` of its settings. In production it is the real provider's; locally both point at one issuer each (`/telegram`, `/google`) of the `mock-oidc` compose service, whose sign-in form accepts any username as the `sub` and any extra claims, so a local sign-in needs no real client (README, Signing in locally). Its tokens carry the host they were requested on as `iss`, so the browser and the backend container both reach it as `mock-oidc.localhost:8080`: browsers resolve `*.localhost` to the local machine, and inside compose the name is a network alias of the service. Its claims are read by their standard OIDC names, and `email` is kept only when `email_verified` is true. The ID token's `iss` must equal the discovery document's `issuer` or one of the entry's `issuer_aliases`: Google issues tokens with `accounts.google.com` as well as `https://accounts.google.com`. Users are matched by provider and `sub`; Telegram's `sub` is not the Telegram user id, which is the separate `id` claim.

A signed-in user links another provider with `POST /user/auth/link/{provider}`. It takes the same client parameters as authorize and the Bearer token, and answers the provider URL as JSON, because a browser redirect cannot carry the Bearer header. A user has at most one identity per provider, so a provider already linked answers 409 `PROVIDER_ALREADY_LINKED`. The request row keeps `link_user_id`. Its callback never attaches the identity itself, since the browser that reaches it is not proven to be the signed-in client: a forged link could otherwise attach an attacker's identity to the victim. Like sign-in, it stores the verified identity on the row (`link_identity`) with the hash of a one-time code and redirects to the client with that code. The client finishes with `POST /user/auth/link/{provider}/complete`, sending the code, its `redirect_uri` and the PKCE `code_verifier` with its Bearer token. The code is checked exactly as at the token endpoint, and it must belong to a link request of the Bearer user for that provider. Only then is it marked used and its `link_identity` cleared. The callback checks no owner, since it does not yet know the signed-in client, and completion reads the identity's owner itself, because time passes between callback and completion. A free identity is attached and completion answers `linked` (`LinkResult` in `app/schemas/user/authorization_request.py`); one that already belongs to the same user answers `linked` too. An identity of another user is never moved by the link: completion records that user as the row's `merge_user_id`, stores the hash of a new merge code that lives 10 minutes (`merge_code_hash`, `merge_expires_at`) and answers `merge_required` with a `MergeOffer`, the code and what a merge would move: the other user's username and base currency, the count of their active ASSET and LIABILITY accounts and of their active transactions, and `is_base_currency_mismatch`, true only when both users have a base currency and they differ. A link code is never accepted by `POST /user/auth/token`. A provider linked meanwhile answers 409 `PROVIDER_ALREADY_LINKED`. The unique constraints on `external_users` (`provider, external_id` and `user_id, provider`) close the remaining race: their violations map to the same two errors (`user_service.add_external_user`). On the sign-in callback a violation rolls the request back, the row's `used` mark included, and redirects to the client with `error=server_error` through `ClientRedirect` (`app/exceptions/temporary_redirect_307.py`). It carries the log message, logger and level of the violation it replaces, and its handler in `app/main.py` logs that entry once and answers the redirect. Accounts are never merged by email, because Telegram returns none. `DELETE /user/auth/link/{provider}` removes the identity, locking the user's identities first so that two concurrent calls cannot remove the last one, which answers 409 `LAST_IDENTITY_UNLINK_FORBIDDEN`.

## Base currency

A user is created without a base currency (`users.base_currency` is nullable), so that signing in needs nothing but the provider's answer. The client chooses it once afterwards with `PUT /user/me/base_currency` (`user_service.set_base_currency`), which also creates the default ledger accounts in one batch (`account_service.create_default_accounts`): an ASSET account named "Wallet" in that currency, an EXPENSE account for each standard category with its type (listed in `account_service.DEFAULT_CATEGORIES`), which the user can rename, delete or add to, and the EQUITY account named "Adjustments". It cannot be changed: a second call with another currency answers 409 `BASE_CURRENCY_ALREADY_SET`, because every stored `base_currency_amount` is in that currency. The update only matches a row whose currency is still null, so two concurrent calls cannot both create the default accounts. A repeated call with the stored currency returns the user unchanged, so a client can retry it safely. Until it is set, `user_service.get_user_base_currency` answers 409 `BASE_CURRENCY_NOT_SET`, which tells the client to show onboarding. The client learns it up front from `GET /user/me` (`user_service.get_user`), which works before onboarding and returns `base_currency` as null until it is set. Reads keep working, but creating an account, location or transaction is refused with that 409: the create endpoints take the user id from `get_onboarded_user_id` (`app/api/deps.py`), which asks `get_user_base_currency` first. So a user has no accounts until the base currency is set, and the default accounts cannot collide with an existing name.

## Username

`PUT /user/me/username` (`user_service.set_username`) changes the username and returns the user, as `PUT /user/me/base_currency` does. `UsernameSet` (`app/schemas/user/user.py`) strips and lowercases the input and accepts 3 to 32 characters of `a-z`, `0-9`, `.`, `_` and `-`; its pattern also lists `A-Z` because Pydantic checks the pattern before it lowercases. The rule covers new input only, so a provider username kept at registration may stay as it came, up to 64 characters in any case. Usernames are unique regardless of case: `uq_users_username_lower` (`app/models/user/user.py`) is a unique index on `lower(username)`, and its violation answers 409 `USERNAME_ALREADY_TAKEN`. Setting the current username again returns the user unchanged, while a change of case of one's own username is a change.

## Currencies

Currencies live in the `currencies` table (`app/models/accounting/currency.py`), which belongs to no user. Its primary key is the ISO 4217 code and it holds the display name, so it is the one table whose key is not a UUIDv7. The initial revision inserts the supported currencies (USD, EUR, RSD, GEL, TRY and RUB); adding or removing one is left to a future admin. `GET /dictionaries/accounting` (`dictionary_service.get_accounting_dictionaries`) is the one dictionary endpoint of the accounting domain (`.claude/rules/common.md` **Architecture**): it returns the currencies ordered by code as key and label pairs, and later value sets of the domain are added to the same response. Every currency field references the table by code: `users.base_currency`, `accounts.currency` and the `source_currency` and `destination_currency` of a transaction are foreign keys to `currencies.code`, and the schemas take them as `CurrencyCode`, a three-letter string. The OpenAPI schema therefore lists no values, and the client reads them from the dictionary. The service checks a code before it writes it (`currency_service.get_currency`), so an unknown one answers 404 `ENTITY_NOT_FOUND` instead of a foreign key violation: when the base currency is set, when an account is created, and for both currencies of every transaction in the base processor's `create`. The test schema is built from the models' metadata, so the `engine` fixture in `tests/conftest.py` inserts the same currency rows the initial revision does.

## Ledger accounts

Everything money moves between is a row of `accounts` (`app/models/accounting/account.py`) with a `kind` (`AccountKind` in `app/schemas/accounting/account.py`): ASSET and LIABILITY accounts hold money, EXPENSE accounts are the categories, INCOME accounts are the income sources, and EQUITY holds the one "Adjustments" account. Only ASSET and LIABILITY accounts (`MONEY_ACCOUNT_KINDS`) have a `currency`, and only EXPENSE accounts have a `category_type`; the check constraints `account_currency_by_kind` and `account_category_type_by_kind` keep both, and `AccountCreateRequest` checks the same before the database does. LIABILITY accounts are created and listed, and move money like ASSET accounts. Only the money kinds cache balances (**Postings**), so the others show 0, and the summary sums the money kinds only (`account_crud.get_active_money_accounts`).

`/accounting/accounts` serves every kind but EQUITY: one request shape creates any of them, and the list takes `kinds` (every kind but EQUITY by default, `VISIBLE_ACCOUNT_KINDS`), `statuses` (ACTIVE by default, so the client lists deleted accounts with `statuses=DELETED`) and `search_term` as one query parameter model. EQUITY is never created, edited, deleted or restored through the API: those calls answer 404 for it, while `GET /accounting/accounts/{account_id}` and an explicit `kinds=EQUITY` still show it. `AccountKind` and its labels, `ACCOUNT_KIND_LABELS`, are served by `GET /dictionaries/accounting` as `account_kinds`.

A deleted EXPENSE account of an expense or INCOME account of an income answers 422 `ACCOUNT_KIND_MISMATCH` (`TransactionProcessor._validate_counter_account`), since it is not an account the transaction may use. The money side of every transaction must be an ASSET or LIABILITY account, which `_validate_account_is_active` checks after the not-found and deleted checks, with the same 422.

Every EXPENSE account has a required category type that classifies the spending it holds: VARIABLE (recurring, with an amount that changes, such as groceries or transport), FIXED (recurring with about the same amount, such as rent, utilities or subscriptions) and PERIODIC (less often than monthly, often large but predictable, such as travel, devices or gifts). These are the three expense groups of budgeting, and future budgets and reports group by them. `CategoryType` and `CATEGORY_TYPE_LABELS` live next to `AccountKind`; `GET /dictionaries/accounting` serves them as `category_types` in the enum's order. `PUT /accounting/accounts/{account_id}` changes the name, description and color of any account but EQUITY, and the type of an EXPENSE account; a type sent for another kind answers 422 `ACCOUNT_KIND_MISMATCH`, and `AccountUpdate` refuses an explicit null, since the type is required.

## Deleted accounts

Every delete in the API is a soft delete and answers 200 with the deleted object, its status DELETED, so the client can update its cache and offer an undo without another request. Transactions, accounts and locations follow it.

Deleting an account is a soft delete: `account_service.delete_account` sets its status to DELETED and returns the account. An ASSET or LIABILITY account can be deleted only with a zero balance, and never when it is the user's last active ASSET or LIABILITY account, which answers 403 `LAST_ACCOUNT_DELETION_FORBIDDEN`. Both checks run under one lock of all the user's active money accounts, taken in one query in id order (`account_crud.get_locked_active_money_accounts`), the order the transaction processors' `get_locked_by_ids` uses too, so two concurrent deletes cannot remove the last two and cannot deadlock. A zero balance with a base value left over, which a deletion of a transaction can leave, would drop that value from the summary total, so `account_service._write_off_base_balance` first writes it off: an ADJUSTMENT dated today with two postings of amount 0, one taking the value off the account and one moving it to the user's EQUITY account (a user without one answers 404 `ENTITY_NOT_FOUND`); the account is first read without a lock only to learn its kind, which never changes; an EXPENSE or INCOME account can be deleted at any time, and the transactions that already reference it keep it and still return it, while a new one cannot use it. Account names are unique per kind among a user's active accounts only. `account_unique_user_id_kind_name` (`app/models/accounting/account.py`) is a partial unique index over `(user_id, kind, name)` of the rows whose status is ACTIVE, so an income source and a money account may share a name, a deleted account frees its name for create and update, and two active accounts of one kind still cannot share one: a violation of that index (`ACCOUNT_UNIQUE_NAME_INDEX`) on create, update or restore answers 409 `NAME_ALREADY_EXISTS` at INFO (`NameAlreadyExists`), while any other integrity violation keeps 409 `INTEGRITY_ERROR` through `IntegrityException` (`account_service._get_integrity_exception`).

`POST /accounting/accounts/{account_id}/restore` (`account_service.restore_account`) turns a deleted account back into an active one. It locks the user's account with that id and status DELETED, as `delete_account` locks an active one, so an unknown or already active account answers 404 `ENTITY_NOT_FOUND`. A deleted money account always has a zero balance, so restoring changes only the status. When an active account already holds the name, the partial index refuses the restore with 409 `NAME_ALREADY_EXISTS`, and the user renames the active account first.

Locations are deleted and restored the same way (`location_service.delete_location`, `restore_location`), each in one conditional update of the row with the expected status, since a location holds no balance and needs no lock. `GET /accounting/locations` takes `statuses` (ACTIVE by default) like the account list, and get, update and delete see active locations only. `location_unique_user_id_name` (`app/models/accounting/location.py`) is a partial unique index over `(user_id, name)` of the active rows, and its violation on create, update or restore answers 409 `NAME_ALREADY_EXISTS` (`location_service._get_integrity_exception`). An expense with a deleted location answers 404 `ENTITY_NOT_FOUND`, since the expense processor reads it through `location_service.get_location`; past transactions keep the reference.

A transaction that touches a deleted account can be neither created nor deleted until the account is restored: both would change the balance of an account the user cannot see. The two account validations of the base processor (`app/services/accounting/transaction_processor/base.py`) answer 403 `DELETED_ACCOUNT_TRANSACTION_FORBIDDEN` on creation, which covers all three types and both sides of a transfer. `delete` locks the money accounts of the transaction's postings and refuses before it marks the transaction deleted. A future transaction edit follows the same rule.

## Transaction amounts

A transaction is a header row of `transactions` (`app/models/accounting/transaction.py`): type, date, status, comment, `location_id` of an expense, `income_period` of an income, and the positive `base_currency_amount` that the list sorts and filters by and the summary sums, null for an expense not valued yet (**Unvalued expenses**), which the list sorts last either way. The check constraints `transaction_location_by_type` and `transaction_income_period_by_type` keep the two type-specific columns filled for their type only. The money it moves is two rows of `postings` (`app/models/accounting/posting.py`), each with an account, a signed `amount` in its own `currency` and a signed `base_amount`. The debit has the negative amounts and the credit the positive ones; their base amounts sum to zero, and each is the header's `base_currency_amount` in size. A credit may carry two more postings of an exchange difference (**Exchange differences**), whose amounts are 0. The processors write the header and its postings in one call (`transaction_crud.create_with_postings`).

| Type | Debit | Credit |
|---|---|---|
| Expense | the money account, in its currency | the EXPENSE account, in the seller's currency |
| Income | the INCOME account, in the payer's currency | the money account, in its currency |
| Transfer | the source money account | the receiving money account |
| Adjustment | the EQUITY account, or the account for a decrease | the account for an increase, or the EQUITY account |

`Transaction` (`app/schemas/accounting/transaction.py`) returns the header and its `postings`, each with its whole account (`Posting` in `app/schemas/accounting/posting.py`). The relationship is ordered by amount with the zero amounts last, so the debit comes first, the credit second and an exchange difference after them, and an adjustment shows its EQUITY posting too.

The list (`transaction_crud.get_transactions`) reads the kinds of the requested `account_ids` and groups them: ASSET and LIABILITY form one money group, and every other kind its own. Each group is one condition on `postings.account_id`, so accounts of one group match either side of a transaction with OR, while the groups combine with AND: a card and a category list the card's expenses in that category, which the client's separate account, category and income source filters rely on. An id that is not one of the user's accounts lists nothing, even next to known ones, since dropping it would lift its kind's condition and widen the list. The list breaks ties by id in the direction of the first order; a UUIDv7 id follows creation, so the four orders of the dictionary, which name one field each, keep a day's transactions in the order they were entered. Without `date_from` the list has no lower bound, so the client pages through the whole history. `TransactionType` with `TRANSACTION_TYPE_LABELS` and the four sort orders of `TRANSACTION_ORDER_LABELS`, keyed by their `orders` query value, are served by `GET /dictionaries/accounting` as `transaction_types` and `transaction_orders`.

## Movements

`POST /accounting/transactions` takes one body, `MovementRequest`, which moves money from `from_account_id` to `to_account_id`; the two must differ. The request carries no type: `transaction_service.create_transaction` reads both accounts of the user, without a lock, since a kind never changes, and `factory.get_movement_processor` derives the type from their kinds (`MOVEMENT_TYPES`). A money account to an EXPENSE account is an expense, an INCOME account to a money account is an income, and a money account to a money account is a transfer. Any other pair, EQUITY included, answers 422 `MOVEMENT_NOT_ALLOWED`. An account the user does not have answers 404 `ENTITY_NOT_FOUND`, since its kind cannot be read. The processor then locks and checks the accounts as before.

The fields that belong to one type are optional in the body and checked by the processor (`TransactionProcessor._validate_fields`): an expense needs `location_id` and `destination_amount` and refuses `income_period`, an income needs `income_period` and `destination_amount` and refuses `location_id`, and a transfer refuses both. A missing one answers 422 `FIELD_REQUIRED` and a refused one 422 `FIELD_NOT_ALLOWED`, both naming the field in the message. An expense or a transfer that sends `base_currency_amount` answers 422 `BASE_CURRENCY_AMOUNT_NOT_ALLOWED`, because both derive it from the debited account's rate. `income_period` is moved to the first of its month.

What source and destination mean for a request depends on the transaction type:

- **Expense**: `source_*` is the amount withdrawn from the account, and `destination_*` is the amount in the seller's or recipient's currency.
- **Income**: `source_*` is the incoming amount in its original currency, which may be any currency, and `destination_*` is the amount credited to the receiving account. When `destination_currency` is the base currency, `base_currency_amount` is `destination_amount`, the amount credited; otherwise, when `source_currency` is, it is `source_amount`. A request that sends `base_currency_amount` in either case answers 422 `BASE_CURRENCY_AMOUNT_NOT_ALLOWED`, even with the derived value, as an adjustment does. When neither currency is the base one, the request carries `base_currency_amount`, and an income without it answers 422 `BASE_CURRENCY_AMOUNT_REQUIRED`.
- **Transfer**: `source_*` is the withdrawal from one account, and `destination_*` is the deposit to the other account, which must be a different account. When both currencies are the same, `destination_amount` may be omitted and is set to `source_amount`; a different value answers 422 `TRANSFER_AMOUNT_MISMATCH`. A transfer into the base currency from another one derives `destination_amount` as the base amount of the debit, and a request that sends `destination_amount` answers 422 `DESTINATION_AMOUNT_NOT_ALLOWED`, even with the derived value.
- **Adjustment**: both postings carry the difference between the new and the old balance, in the account currency.

## Postings

A money account (ASSET or LIABILITY) caches the sums of the postings of its active transactions: `balance` of their amounts and `base_balance` of their base amounts. The processor changes the cache of every money account a transaction posts to in the same database transaction (`account_crud.add_to_balance`), and deleting a transaction marks its header DELETED and subtracts its postings again. The other kinds keep a zero cache, since their postings are in several currencies.

An account's rate is never stored. `utils.get_base_currency_rate` derives it as `balance / base_balance`, how many units of the account currency one unit of the base currency buys, rounded to 10 decimal places, and 0 when either sum is 0. The account response shows it as `base_currency_rate` and the base value as `base_currency_balance`, `base_balance` rounded to cents.

A credit brings its own base amount: the income's, or the debit's on the other side of a transfer. A debit is valued at the account's average rate by one pure calculator, `ledger_service.get_base_amount`: the amount itself for an account in the base currency, all of `base_balance` when the debit empties the account (the amount equals the absolute balance), and otherwise `amount * base_balance / balance`, rounded to cents and kept at 0.01 at least, since an amount must be positive. An account outside the base currency has no rate (`ledger_service.has_base_currency_rate`) with a zero balance or base value, or the two of opposite signs, which a deletion can leave. An expense from such an account is stored unvalued (**Unvalued expenses**), while a transfer from it answers 403 `NO_ACCOUNT_BASE_CURRENCY_RATE`, since a transfer into the base currency derives its amount from the base amount. A new debit is valued and checked at the sums on its date, not at the cache (`TransactionProcessor._get_debit_base_amount`, which returns null without a rate, and `ledger_service.get_balances_at_date`, the cache less the active postings dated after it and the expenses still waiting for a value on that date, `posting_crud.get_sums_at_date`), so a back-dated expense from an account that is empty today is valued when the account had a rate on that date. An emptied account loses its rate, so an overdraft of such an account is unvalued until it is credited again; an overdraft of an account that keeps a rate is valued at it.

## Unvalued expenses

A new credit card in a foreign currency has no rate, and the cost of its spending in the base currency is known only when it is repaid. So an expense from an account without a rate is stored with a null `base_currency_amount` and null base amounts on both postings, and adds nothing to the account's `base_balance`. `ledger_service.get_valued_amount` reads a null base amount as 0 wherever base amounts are summed. The constraint trigger `transaction_valuation` (`app/models/accounting/transaction.py`, created by the revision `unvalued_postings`) keeps a transaction either fully valued or fully unvalued: a CHECK cannot read another table, so a deferred trigger on `transactions` and `postings` compares the header with its postings at commit.

The recalculation values them (**Recalculation**). An expense valued by a later credit keeps that credit's date in `transactions.valued_on`. A walk from a date starts no later than the account's first unvalued expense or the first one valued on that date or later (`posting_crud.get_first_revaluable_date`), so a credit dated after them reaches them, and deleting or changing the credit that valued them values them again. The walk treats both kinds as waiting: an expense debit that finds a rate at the running sums is valued at it like any debit and loses its `valued_on`; one that finds none waits, and the next credit that brings its own base amount, an adjustment excepted, values every waiting debit before it at that credit's rate (`get_base_amount` with the credit as the balance), oldest first, with their headers and the EXPENSE postings, and sets their `valued_on` to its date. Debits still waiting when the walk ends return to null. The rate at the running sums leaves the waiting debits out, as `get_balances_at_date` does, since their amounts are in the balance but not in the base value: an adjustment that gives such an account a rate values the next debit at the adjustment's own rate, not at the whole debt's.

The summary keeps them apart: earned and spent sum the valued amounts only, and `unvalued_spent` lists the unvalued expenses of the month as amounts in the currency of the debited account, one per currency in code order (`transaction_crud.get_unvalued_expense_sums`).

## Estimates

An unvalued amount has no base value until a credit values it, so the read responses carry an estimate at today's market rate next to it, computed on read and never stored: `estimated_base_currency_amount` on a transaction and `estimated_base_amount` on its postings (`transaction_service`, on list and get), `estimated_base_balance` on a money account with unvalued debits, its `base_currency_balance` plus those debits at the market rate (`account_service`, on list and get, over `posting_crud.get_unvalued_sums` and `account_service.get_unvalued_estimates`), and on the summary `estimated_total_balance`, the total plus the same unvalued debits at the market rate, and `estimated_unvalued_spent`, the month's `unvalued_spent` in the base currency. A transaction's estimate is its debit's amount at the rate of the debit's currency, and its credit takes the opposite, so the estimated base amounts sum to zero as stored ones do. A field is null when there is nothing to estimate or no rate for it. The responses of writes leave every estimate null, so no outbound call happens while a write's transaction holds its locks; the client reads the estimates from the lists it refetches. A summary total is null when any of its parts has no rate, so it is never a partial sum.

The rates come from `GET /v6/latest/USD` of open.er-api.com (`exchange_rate_settings.url`), a free endpoint without a key that updates once a day. `exchange_rate_service.get_base_currency_rates` keeps the USD rates in process memory for `cache_seconds` (12 hours) and derives the rate of every currency to the user's base currency from them; it is called only when a response has something to estimate, so a request without unvalued amounts never reaches the provider. A provider that fails, answers an error or sends rates `ExchangeRates` refuses is logged at WARNING and changes nothing: the rates cached last stay in use, and with none cached every estimate is null. The next attempt waits `RETRY_SECONDS` (5 minutes), and the attempt time is set before the request goes out, so concurrent requests at expiry make one call and the others answer from the cache. A user without a base currency gets no rates. The provider's terms ask for a link to it wherever its rates are shown, which is the frontend's to show next to an estimate. Tests point the URL at `open.er-api.test` and answer it through `httpx_mock`; the autouse `empty_exchange_rates_cache` fixture in `tests/conftest.py` empties the cache before each test.

## Exchange differences

A credit brings its own base amount, so repaying a debt at another rate than the one the debt was valued at would leave a base value on an account whose balance is 0: a EUR card at -600 EUR worth -660 USD repaid by 600 EUR bought for 650 USD would end at 0 EUR and -10 USD, off the summary total and with no rate. So when a credit that keeps its own base amount takes an account from a balance of 0 or less to 0 or more, the walk computes the exchange difference (`ledger_service.get_exchange_difference`): the base value the account should end with, 0 for a zero balance and otherwise the new balance at the credit's rate, less the running base value and the credit's base amount. A difference other than 0 is posted inside the credit's transaction as two postings of amount 0 in the account's currency: one on the account with the difference and one on the user's EQUITY account, Adjustments, with its opposite, so the base amounts still sum to zero and the header keeps the credit's amount. An adjustment keeps the rate and gets none. The walk keeps these postings current: it updates them when the difference changes, deletes them when it becomes 0 (`posting_crud.delete_by_ids`), creates them when one appears (reading the EQUITY account only then; a user without an active one answers 404 `ENTITY_NOT_FOUND`), and changes the account's `base_balance` cache by the change.

## Recalculation

Valuation follows the order of the transaction dates, not the order of entry. An account's postings are ordered by the transaction date, then by the transaction id, which as a UUIDv7 follows creation. After every create and delete the base processor calls `ledger_service.recalculate_accounts`, which walks each money account of the transaction over its active postings from the transaction's date. The walk starts from the cached sums less the stored postings it is about to walk, not from a sum of the earlier postings, so a cache with no postings behind it keeps its opening value. A credit keeps its base amount; a debit, and either posting of an adjustment on the account, since an adjustment keeps the rate, is valued again by `get_base_amount` at the running sums, and one that finds no rate there keeps its stored base amount, an expense excepted, which waits (**Unvalued expenses**), so a back-dated debit or the deletion of the credit that funded it is never refused. When such a base amount changes, the other posting and the header's `base_currency_amount` change with it, and a money account on the other side of a transfer gets the change in its cache and is walked in turn from the transfer's date. A receiving account in the base currency takes the new value as its amount too, since a transfer into the base currency derives that amount from the debit's base amount and an account in the base currency keeps `balance` equal to `base_balance`. A change only moves to postings later in date order, so the walk ends. A recalculation that leaves the cache of a deleted account changed answers 403 `DELETED_ACCOUNT_TRANSACTION_FORBIDDEN` with that account's id and is rolled back, as creating or deleting a transaction of a deleted account is: the user restores the account first. A deleted account outside the base currency that the walk empties again ends with an unchanged cache and passes. The writes go through `posting_crud.update_amounts`, `transaction_crud.update_base_currency_amounts`, `transaction_crud.update_valued_dates`, `posting_crud.create_batch` and `posting_crud.delete_by_ids` for exchange differences, and `account_crud.add_to_balance`, and the processor reads the transaction again afterwards, so its answer shows the recalculated amounts.

`create` and `delete` lock all of the user's money accounts in id order (`account_crud.lock_money_accounts`) before anything else, `delete` before it locks the transaction row and the processor before it locks its own accounts, whatever their status, since a walk can reach a deleted account through an old transfer. Every account a recalculation reaches is locked before any of them is read, and two requests of one user cannot deadlock or recalculate one account at once.

## Balance adjustments

An ADJUSTMENT transaction (`transaction_processor/adjustment.py`) sets an account to the balance the user enters: the starting balance after onboarding, or the real one when the account drifts from the bank. It is created by `POST /accounting/accounts/{account_id}/adjustment` (`transaction_service.adjust_balance`), which answers the transaction, so the client can delete it to undo. The EQUITY account answers 404 `ENTITY_NOT_FOUND`, as every other account call on it does. The body, `AdjustmentRequest`, carries `new_balance`, not amounts, and the service passes it with the path's account as `AdjustmentCreate` to the processor. It lives in `transaction_service` rather than `account_service`, because the processors import `user_service`, which imports `account_service`. The processor locks the account, computes the difference and posts it between the account and the user's EQUITY account, Adjustments: an increase credits the account and a decrease debits it. A user without an active EQUITY account answers 404 `ENTITY_NOT_FOUND`. A new balance equal to the current one answers 422 `ACCOUNT_BALANCE_UNCHANGED`. `base_currency_amount` is the difference valued by `ledger_service.get_base_amount` at the sums on the adjustment's date when the account is in the base currency or has a rate there, so an adjustment keeps the rate; an account outside the base currency without a rate takes it from the request, and answers 403 `NO_ACCOUNT_BASE_CURRENCY_RATE` without it. That also covers a decrease of an empty account below zero, such as the starting balance of a credit card, which then has a rate for its debts. A request that sends `base_currency_amount` for an account that has a rate answers 422 `BASE_CURRENCY_AMOUNT_NOT_ALLOWED` instead of having the value silently ignored. The not-found and deleted-account checks are the base processor's `_validate_account_is_active`, shared by the adjustment and the account validations of the other types. The currencies of an adjustment are the locked account's, so `create` checks no currency for it (`_get_request_currencies`), while the other types check the distinct currencies of the request before the processor reads any account. Adjustments are neither income nor expense: reports that sum incomes and expenses read only those two types. An adjustment is deleted like any other transaction, which moves the balance back.

## Summary

An account's balance in the base currency is its cached `base_balance` rounded to cents. The account response exposes it as the computed `base_currency_balance`, and `GET /accounting/summary` (`summary_service.get_summary`) sums the same rounded values of the user's active ASSET and LIABILITY accounts as `total_balance`, so the total always equals the sum of the balances the client shows. The summary takes `month`, any date inside the month and today's month by default, and answers its first day. The backend works in UTC throughout, so that default is the UTC date; time zones belong to the frontend, which sends `month` when the user's local month differs. Earned and spent are the sums of `base_currency_amount` of the active income and expense transactions dated inside the month, read in one aggregate query, which skips unvalued expenses; left over is their difference and may be negative. `unvalued_spent` lists those expenses by currency (**Unvalued expenses**), and `estimated_total_balance` and `estimated_unvalued_spent` estimate what is left unvalued (**Estimates**).

## Migrations

The application is deployed, and the production database is stamped with the revisions in `db_migration/versions/`. So every schema change adds a new revision on top with `alembic revision --autogenerate`; an existing revision is never edited, deleted or regenerated, since the production database could no longer find it and `alembic upgrade head`, which every deploy runs before the new backend starts, would fail. The previous backend keeps serving on the new schema until the new one replaces it, so a revision that drops or renames a column, or adds a `NOT NULL` column without a default, ships in two deploys: first the code that no longer uses the old shape, then the revision.
