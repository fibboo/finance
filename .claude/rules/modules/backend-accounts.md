# backend: accounts, locations and currencies

## Currencies

Currencies live in the `currencies` table (`app/models/accounting/currency.py`), which belongs to no user. Its primary key is the ISO 4217 code and it holds the display name, so it is the one table whose key is not a UUIDv7. The initial revision inserts the supported currencies (USD, EUR, RSD, GEL, TRY and RUB); adding or removing one is left to a future admin. `GET /dictionaries/accounting` (`dictionary_service.get_accounting_dictionaries`) is the one dictionary endpoint of the accounting domain (`.claude/rules/common.md` **Architecture**): it returns the currencies ordered by code as key and label pairs, and later value sets of the domain are added to the same response. Every currency field references the table by code: `users.base_currency`, `accounts.currency` and the `source_currency` and `destination_currency` of a transaction are foreign keys to `currencies.code`, and the schemas take them as `CurrencyCode`, a three-letter string. The OpenAPI schema therefore lists no values, and the client reads them from the dictionary. The service checks a code before it writes it (`currency_service.get_currency`), so an unknown one answers 404 `ENTITY_NOT_FOUND` instead of a foreign key violation: when the base currency is set, when an account is created, and for both currencies of every transaction in the base processor's `create`. The test schema is built from the models' metadata, so the `engine` fixture in `tests/conftest.py` inserts the same currency rows the initial revision does.

## Ledger accounts

Everything money moves between is a row of `accounts` (`app/models/accounting/account.py`) with a `kind` (`AccountKind` in `app/schemas/accounting/account.py`): ASSET and LIABILITY accounts hold money, EXPENSE accounts are the categories, INCOME accounts are the income sources, and EQUITY holds the one "Adjustments" account. Only ASSET and LIABILITY accounts (`MONEY_ACCOUNT_KINDS`) have a `currency` and may have a `color`, and only EXPENSE accounts have a `category_type`; the check constraints `account_currency_by_kind`, `account_color_by_kind` and `account_category_type_by_kind` keep them, and `AccountCreateRequest` checks the same before the database does. The color only tells money accounts apart, so categories, income sources and the EQUITY account have none. LIABILITY accounts are created and listed, and move money like ASSET accounts. Only the money kinds cache balances (**Postings** in `backend-ledger.md`), so the others show 0, and the summary sums the money kinds only (`account_crud.get_active_money_accounts`).

`/accounting/accounts` serves every kind but EQUITY: one request shape creates any of them, and the list takes `kinds` (every kind but EQUITY by default, `VISIBLE_ACCOUNT_KINDS`), `category_types` (empty by default, which filters nothing; a non-empty value keeps only the accounts whose category type is in it, so accounts of other kinds, which have none, drop out), `statuses` (ACTIVE by default, so the client lists deleted accounts with `statuses=DELETED`) and `search_term` as one query parameter model. EQUITY is never created, edited, deleted or restored through the API: those calls answer 404 for it, while `GET /accounting/accounts/{account_id}` and an explicit `kinds=EQUITY` still show it. `AccountKind` and its labels, `ACCOUNT_KIND_LABELS`, are served by `GET /dictionaries/accounting` as `account_kinds`.

A deleted EXPENSE account of an expense or INCOME account of an income answers 422 `ACCOUNT_KIND_MISMATCH` (`TransactionProcessor._validate_counter_account`), since it is not an account the transaction may use. The money side of every transaction must be an ASSET or LIABILITY account, which `_validate_account_is_active` checks after the not-found and deleted checks, with the same 422.

Every EXPENSE account has a required category type that classifies the spending it holds: VARIABLE (recurring, with an amount that changes, such as groceries or transport), FIXED (recurring with about the same amount, such as rent, utilities or subscriptions) and PERIODIC (less often than monthly, often large but predictable, such as travel, devices or gifts). These are the three expense groups of budgeting, and future budgets and reports group by them. `CategoryType` and `CATEGORY_TYPE_LABELS` live next to `AccountKind`; `GET /dictionaries/accounting` serves them as `category_types` in the enum's order. `PUT /accounting/accounts/{account_id}` changes the name and description of any account but EQUITY, the color of a money account and the type of an EXPENSE account; a color or a type sent for another kind answers 422 `ACCOUNT_KIND_MISMATCH`, and `AccountUpdate` refuses an explicit null, since the type is required.

## Deleted accounts

Every delete in the API is a soft delete and answers 200 with the deleted object, its status DELETED, so the client can update its cache and offer an undo without another request. Transactions, accounts and locations follow it.

Deleting an account is a soft delete: `account_service.delete_account` sets its status to DELETED and returns the account. An ASSET or LIABILITY account can be deleted only with a zero balance, and never when it is the user's last active ASSET or LIABILITY account, which answers 403 `LAST_ACCOUNT_DELETION_FORBIDDEN`. Both checks run under one lock of all the user's active money accounts, taken in one query in id order (`account_crud.get_locked_active_money_accounts`), the order the transaction processors' `get_locked_by_ids` uses too, so two concurrent deletes cannot remove the last two and cannot deadlock. A zero balance with a base value left over, which a deletion of a transaction can leave, would drop that value from the summary total, so `account_service._write_off_base_balance` first writes it off: an ADJUSTMENT dated today with two postings of amount 0, one taking the value off the account and one moving it to the user's EQUITY account (a user without one answers 404 `ENTITY_NOT_FOUND`); the account is first read without a lock only to learn its kind, which never changes; an EXPENSE or INCOME account can be deleted at any time, and the transactions that already reference it keep it and still return it, while a new one cannot use it. `GET /accounting/accounts/{account_id}` answers such a deleted account too, so that the client can show the category or income source of a past transaction and offer to restore it; a deleted money account answers 404 there, since the client never opens one. Account and location names are 3 to 32 characters; the client cuts or wraps a long name where a row, card or panel has no room for it, and a longer text belongs in the description. Account names are unique per kind among a user's active accounts only. `account_unique_user_id_kind_name` (`app/models/accounting/account.py`) is a partial unique index over `(user_id, kind, name)` of the rows whose status is ACTIVE, so an income source and a money account may share a name, a deleted account frees its name for create and update, and two active accounts of one kind still cannot share one: a violation of that index (`ACCOUNT_UNIQUE_NAME_INDEX`) on create, update or restore answers 409 `NAME_ALREADY_EXISTS` at INFO (`NameAlreadyExists`), while any other integrity violation keeps 409 `INTEGRITY_ERROR` through `IntegrityException` (`account_service._get_integrity_exception`).

`POST /accounting/accounts/{account_id}/restore` (`account_service.restore_account`) turns a deleted account back into an active one. It locks the user's account with that id and status DELETED, as `delete_account` locks an active one, so an unknown or already active account answers 404 `ENTITY_NOT_FOUND`. A deleted money account always has a zero balance, so restoring changes no balance. When an active account already holds the name, the partial index refuses the restore with 409 `NAME_ALREADY_EXISTS`. A deleted account cannot be renamed, so the restore takes an optional new name and writes it in the same update as the status: the account is never active under the old name, and a taken new name is refused by the same index.

Locations are deleted and restored the same way (`location_service.delete_location`, `restore_location`), each in one conditional update of the row with the expected status, since a location holds no balance and needs no lock. `GET /accounting/locations` takes `statuses` (ACTIVE by default) like the account list, and get, update and delete see active locations only. `location_unique_user_id_name` (`app/models/accounting/location.py`) is a partial unique index over `(user_id, name)` of the active rows, and its violation on create, update or restore answers 409 `NAME_ALREADY_EXISTS` (`location_service._get_integrity_exception`). An expense with a deleted location answers 404 `ENTITY_NOT_FOUND`, since the expense processor reads it through `location_service.get_location`; past transactions keep the reference.

A transaction that touches a deleted account can be neither created nor deleted until the account is restored: both would change the balance of an account the user cannot see. The two account validations of the base processor (`app/services/accounting/transaction_processor/base.py`) answer 403 `DELETED_ACCOUNT_TRANSACTION_FORBIDDEN` on creation, which covers all three types and both sides of a transfer. `delete` locks the money accounts of the transaction's postings and refuses before it marks the transaction deleted, and `update` refuses the same way before it replaces the postings, while its new accounts go through the creation checks.
