# backend: users and sign-in

## Tokens

The API authenticates by a short-lived HS256 JWT access token (`app/services/user/token_service.py`). `get_user_id` (`app/api/deps.py`) checks its signature and expiry and returns its `sub` without reading the database, so an access token stays valid until it expires even after its refresh token is revoked.

Refresh tokens rotate: each use revokes the presented token and issues a new one in the same family. Presenting a token that is already revoked means it was copied, so the whole family is revoked (reuse detection). That revocation must outlive the 401 it answers with, while `DbTransaction` rolls a request back on any exception. So `_get_db_transaction` commits before re-raising `RefreshTokenReusedException`, and only that one.

The backend serves web clients only. The refresh token never appears in a response body: `POST /user/auth/token` answers the access token as JSON and sets the refresh token as the `refresh_token` cookie, `HttpOnly; Secure; SameSite=Strict` with `Path=/user/auth` and `Max-Age` of `refresh_token_expire_seconds` (`app/api/cookies.py`, which defines the name and attributes once). The handler calls `auth_service.grant_token`, which picks the grant, and hands the token pair to `cookies.build_token_response`, which sets the cookie and returns the body. The frontend proxy rewrites the path to where it serves the API (`.claude/rules/react.md` **Auth and Security**); the backend knows nothing about that. `Secure` stays on everywhere. Chromium and Firefox treat `http://localhost` as a secure context and accept the cookie there, while Safari may drop it, so local development uses Chrome or Firefox. Both grants of `POST /user/auth/token` and `POST /user/auth/revoke` read the cookie through `get_refresh_token` (`app/api/deps.py`), which also answers 403 `ORIGIN_NOT_ALLOWED` when an `Origin` header is present and not in `allowed_origins`, as a CSRF defence next to `SameSite=Strict`. `allowed_origins` holds the frontend's origin, since the proxy serves the API from it. A refresh grant without the cookie is answered 401 `INVALID_TOKEN` by `auth_service.grant_token`. `/revoke` without the cookie answers 200 and only clears it, since RFC 7009 has a revocation always succeed. The authorization code grant revokes the family of a cookie it is sent before it issues a new family, so a second sign-in in the same browser leaves no live token behind. A refresh grant that fails with an unknown, expired or reused token raises a `RefreshTokenRejectedException`, whose handler in `app/main.py` clears the cookie on the 401. `/revoke` clears the cookie.

## Sign-in

The backend is the OpenID Connect client towards the providers and the authorization server towards our own clients (`app/services/user/auth/auth_service.py`). A client opens `GET /user/auth/authorize/{provider}` with its `redirect_uri`, its own `state` and a PKCE S256 `code_challenge`. These query parameters arrive as one model, `AuthorizeRequest` (`app/schemas/user/authorization_request.py`), which checks them: the method is `S256`, the challenge is 43 base64url characters and the state is 1 to 512 characters. `POST /user/auth/link/{provider}` takes the same model, and the provider callback takes `CallbackRequest`. The handlers pass the models to the service as they are, and the two redirecting handlers declare `response_class=RedirectResponse` with status 307 and return the URL, so no handler builds a response itself and OpenAPI documents a redirect. The `redirect_uri` must be in `allowed_redirect_uris`, since the one-time code is sent there. An `authorization_requests` row keeps our own `state`, `nonce` and provider PKCE verifier next to what the client sent, and the client is redirected to the provider. If the provider's discovery document cannot be fetched, is not JSON or has no `authorization_endpoint`, the call answers 502 `PROVIDER_UNAVAILABLE`.

The provider returns to `GET /user/auth/callback/{provider}`. The code is exchanged and the ID token is checked against the provider's JWKS, `iss`, `aud`, `exp` and `nonce` (`oidc_provider.py`). The user is found by provider and `sub`, or created. A new user takes the provider's username, or a fallback when the provider sends none, the username belongs to another user in any case (`user_crud.get_user_by_username` compares `lower(username)`, which the unique index serves), or it is shorter than 3 or longer than 64 characters (what `users.username` holds). The fallback is `user_` followed by 8 random lowercase letters and digits (`user_service.FALLBACK_USERNAME_*`), so it never shows the provider's id and cannot be taken in advance for a given identity; a fallback that is already taken is generated again, up to 5 times. `external_users.username` keeps the provider's own username, and the user's fallback only when the provider sends none; a linked identity without a username gets a fallback of its own. A claim of the wrong type is dropped, as is a `picture` the `users.avatar` column cannot hold (3 to 2560 characters), so the user is created without it; an ID token without a string `sub` redirects with `server_error`. The row gets the hash of a one-time code that lives one minute. An unknown `state` answers 401, because there is no trusted client to redirect to. An expired or already completed one redirects to the client redirect URI stored on its row with `error=expired_request` through `ClientRedirect` and writes nothing. A provider error, a failed code exchange, a discovery document, token response or JWKS that is not JSON, a token response without an ID token, a discovery document without `issuer` or `jwks_uri`, a rejected ID token or a new user for whom the provider username and every fallback are taken redirects to the client with `error` (`server_error` for all but the provider's own error, `invalid_request` for a callback without a code) and marks the row used, so its `state` cannot be completed later, and writes nothing else. The one exception is the race on the unique constraints described below, whose transaction is rolled back, so the row stays unused until it expires 10 minutes after it was created. The callback's `state` is bounded in length. A provider `error` outside the RFC 6749 error characters or longer than 128 characters is replaced by `invalid_request` before it goes into the redirect. `POST /user/auth/token` with `grant_type=authorization_code` accepts the code once, for the same `redirect_uri`, with the verifier matching the stored challenge. An unknown, used or expired code answers 401 `INVALID_TOKEN` alike, as RFC 6749 names all of them `invalid_grant`.

Each call builds a fresh Authlib client, so the discovery document and the JWKS are fetched per request instead of cached in the process. A provider is one entry in `providers.py`: Telegram and Google. Each entry reads its discovery URL from `server_metadata_url` of its settings. In production it is the real provider's; locally both point at one issuer each (`/telegram`, `/google`) of the `mock-oidc` compose service, whose sign-in form accepts any username as the `sub` and any extra claims, so a local sign-in needs no real client (README, Signing in locally). Its tokens carry the host they were requested on as `iss`, so the browser and the backend container both reach it as `mock-oidc.localhost:8080`: browsers resolve `*.localhost` to the local machine, and inside compose the name is a network alias of the service. Its claims are read by their standard OIDC names, and `email` is kept only when `email_verified` is true. The ID token's `iss` must equal the discovery document's `issuer` or one of the entry's `issuer_aliases`: Google issues tokens with `accounts.google.com` as well as `https://accounts.google.com`. Users are matched by provider and `sub`; Telegram's `sub` is not the Telegram user id, which is the separate `id` claim.

A signed-in user links another provider with `POST /user/auth/link/{provider}`. It takes the same client parameters as authorize and the Bearer token, and answers the provider URL as JSON, because a browser redirect cannot carry the Bearer header. A user has at most one identity per provider, so a provider already linked answers 409 `PROVIDER_ALREADY_LINKED`. The request row keeps `link_user_id`. Its callback never attaches the identity itself, since the browser that reaches it is not proven to be the signed-in client: a forged link could otherwise attach an attacker's identity to the victim. Like sign-in, it stores the verified identity on the row (`link_identity`) with the hash of a one-time code and redirects to the client with that code. The client finishes with `POST /user/auth/link/{provider}/complete`, sending the code, its `redirect_uri` and the PKCE `code_verifier` with its Bearer token. The code is checked exactly as at the token endpoint, and it must belong to a link request of the Bearer user for that provider. Only then is it marked used and its `link_identity` cleared. The callback checks no owner, since it does not yet know the signed-in client, and completion reads the identity's owner itself, because time passes between callback and completion. A free identity is attached and completion answers `linked` (`LinkResult` in `app/schemas/user/authorization_request.py`); one that already belongs to the same user answers `linked` too. An identity of another user is never moved by the link: completion records that user as the row's `merge_user_id`, stores the hash of a new merge code that lives 10 minutes (`merge_code_hash`, `merge_expires_at`) and answers `merge_required` with a `MergeOffer`, the code and what a merge would move: the other user's username and base currency, the count of their active ASSET and LIABILITY accounts and of their active transactions, `is_base_currency_mismatch`, true only when both users have a base currency and they differ, and `is_provider_conflict`, true when both users have an identity of the same provider (`merge_service.is_base_currency_mismatch` and `get_shared_providers` decide both, for the offer and the merge alike). A link code is never accepted by `POST /user/auth/token`. A provider linked meanwhile answers 409 `PROVIDER_ALREADY_LINKED`. The unique constraints on `external_users` (`provider, external_id` and `user_id, provider`) close the remaining race: their violations map to the same two errors (`user_service.add_external_user`). On the sign-in callback a violation rolls the request back, the row's `used` mark included, and redirects to the client with `error=server_error` through `ClientRedirect` (`app/exceptions/temporary_redirect_307.py`). It carries the log message, logger and level of the violation it replaces, and its handler in `app/main.py` logs that entry once and answers the redirect. Accounts are never merged by email, because Telegram returns none. `DELETE /user/auth/link/{provider}` removes the identity, locking the user's identities first so that two concurrent calls cannot remove the last one, which answers 409 `LAST_IDENTITY_UNLINK_FORBIDDEN`.

## Account merge

`POST /user/auth/merge` (`merge_service.merge`) takes the offer's merge code with the Bearer token. The row is found by the hash of the code (`authorization_request_crud.get_by_merge_code_hash`), and an unknown or expired code, or one issued to another user, answers 401 `INVALID_TOKEN`. Both users are then locked in id order, and only then the row, checked again, and their money accounts, so two overlapping merges always lock in the same order and cannot deadlock, and no transaction of either user is created in the middle. Different base currencies answer 409 `BASE_CURRENCY_MISMATCH` and an identity of the same provider on both users 409 `PROVIDER_ALREADY_LINKED`, since a user holds one identity per provider and dropping one would lose a way to sign in. A user without a base currency has no data, and when it is the current one, it takes the other's. Active EXPENSE, INCOME and EQUITY accounts and active locations that share a name with an active one of the current user fold into it: the other user's postings and transactions are re-pointed and the emptied row is deleted, which moves no money between money accounts. Every other account and location moves, and an active ASSET or LIABILITY account whose name is taken gets the first free numeric suffix (`Wallet 2`), cut to fit 32 characters, the length of `accounts.name`. The other user's transactions and identities move too, its refresh tokens and every `authorization_requests` row that references it are deleted, since none of those foreign keys has `ON DELETE`, and finally the user itself. Deleting the request row uses up the code. The current user's username and avatar stay, and the answer is the current `User` with its new identities. Everything runs in the request transaction.

## Base currency

A user is created without a base currency (`users.base_currency` is nullable), so that signing in needs nothing but the provider's answer. The client chooses it once afterwards with `PUT /user/me/base_currency` (`user_service.set_base_currency`), which also creates the default ledger accounts in one batch (`account_service.create_default_accounts`): an ASSET account named "Wallet" in that currency, an EXPENSE account for each standard category with its type (listed in `account_service.DEFAULT_CATEGORIES`), which the user can rename, delete or add to, and the EQUITY account named "Adjustments". It cannot be changed: a second call with another currency answers 409 `BASE_CURRENCY_ALREADY_SET`, because every stored `base_currency_amount` is in that currency. The update only matches a row whose currency is still null, so two concurrent calls cannot both create the default accounts. A repeated call with the stored currency returns the user unchanged, so a client can retry it safely. Until it is set, `user_service.get_user_base_currency` answers 409 `BASE_CURRENCY_NOT_SET`, which tells the client to show onboarding. The client learns it up front from `GET /user/me` (`user_service.get_user`), which works before onboarding and returns `base_currency` as null until it is set. Reads keep working, but creating an account, location or transaction is refused with that 409: the create endpoints take the user id from `get_onboarded_user_id` (`app/api/deps.py`), which asks `get_user_base_currency` first. So a user has no accounts until the base currency is set, and the default accounts cannot collide with an existing name.

## Username

`PUT /user/me/username` (`user_service.set_username`) changes the username and returns the user, as `PUT /user/me/base_currency` does. `UsernameSet` (`app/schemas/user/user.py`) strips and lowercases the input and accepts 3 to 32 characters of `a-z`, `0-9`, `.`, `_` and `-`; its pattern also lists `A-Z` because Pydantic checks the pattern before it lowercases. The rule covers new input only, so a provider username kept at registration may stay as it came, up to 64 characters in any case. Usernames are unique regardless of case: `uq_users_username_lower` (`app/models/user/user.py`) is a unique index on `lower(username)`, and its violation answers 409 `USERNAME_ALREADY_TAKEN`. Setting the current username again returns the user unchanged, while a change of case of one's own username is a change.
