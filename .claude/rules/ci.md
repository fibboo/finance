# CI/CD and production

## Production compose

Production runs `docker-compose.production.yml` on the VPS: `backend` and `frontend` run the GHCR images `ghcr.io/fibboo/finance-backend` and `ghcr.io/fibboo/finance-frontend` tagged with `IMAGE_TAG`, next to `postgres` and `cloudflared`, which runs the Cloudflare Tunnel to `frontend`; every service has a healthcheck (the `backend` and `frontend` ones ask `GET /health` of the backend with `wget`, a route of `app/main.py` left out of the OpenAPI schema), `frontend` starts once the `backend` one passes and `cloudflared` once the `frontend` one does (nginx answering `/api/health` through its proxy). No service publishes a port on the public address; `postgres` publishes 5432 on `172.29.172.1` only, the host's address on the Amnezia VPN network (README, Deployment). `backend` reads `backend/.env-production`, whose secrets are `'${VAR}'` placeholders filled with envsubst at deploy time, and runs uvicorn only, since the deploy applies the migrations; the compose file reads `IMAGE_TAG`, `POSTGRES_PASSWORD` and `CLOUDFLARE_TUNNEL_TOKEN` from the project `.env` the deploy writes beside it.

## Workflows

`.github/workflows/tests.yml` runs on every pull request (any base branch) and not on `main`, so a merged commit is deployed on the checks of its pull request. The `changes` job (`dorny/paths-filter`) starts each job only when its files changed: `tests` on `backend/**`, `frontend` on `frontend/**`, `api-schema` on `backend/**`, `frontend/src/lib/api-schema.ts`, `frontend/package.json` or `frontend/package-lock.json`, and all three on `.github/workflows/**`, so a change only to `docs/`, `.claude/`, `README.md` or `CLAUDE.md` runs none. Every job of both workflows runs on the one self-hosted runner on the VPS, which takes one job at a time, so the jobs of a run execute in sequence; the server also serves production on 1 vCPU and 1 GB of RAM, so the runner's unit and the containers the jobs start are limited in memory and CPU, and a job that builds an image ends by pruning dangling images and old build cache (README, Self-hosted runner). The `tests` job builds `backend/tests/Dockerfile` with `backend/` as the context and runs `pytest -v -n auto` inside it. The `frontend` and `api-schema` jobs take Node and `frontend/node_modules` from the composite action `.github/actions/frontend-dependencies`, which hard-links the copy kept in `~/.cache/finance-ci` on the runner while the Node version and `package-lock.json` stay the same and runs `npm ci` otherwise. The `frontend` job runs `lint`, `typecheck`, a Prettier check, `test` and `build` in `frontend/` with a Node heap limit of 2 GB, since Node sizes its default heap from the server's 1 GB of RAM. The `api-schema` job starts the backend image with `backend/.env` as the container `finance-api-schema` on `127.0.0.1:8000`, runs `generate:api` against it, fails when the committed `api-schema.ts` differs and removes the container whatever the outcome, since the runner outlives the job. `.github/workflows/deploy.yml` runs on every push to `main`, one deploy at a time with the newest waiting push replacing the older waiting ones, and on `workflow_dispatch` from any branch. It checks that every secret is set and has no single quote, renders `backend/.env-production` and the project `.env` from the repository secrets, builds `backend/Dockerfile` and `frontend/Dockerfile` on the host's Docker layer cache, pushes them to GHCR tagged with the commit SHA from a Docker config of its own, copies the rendered files with `docker-compose.production.yml` into `~/finance` on the same host, without SSH, and runs there `docker compose pull`, `up -d --wait --no-recreate postgres`, a `pg_dump` into `~/backups/pre-deploy-<utc time>-<sha>.dump` (the five newest are kept), `alembic upgrade head` in a one-off container of the new backend image started with `--no-deps`, and `up -d --remove-orphans --wait --wait-timeout 300`, which fails the deploy when a service turns unhealthy or is still starting after five minutes and is the only step that applies changes to postgres, then removes the finance images of other SHAs; a failed dump or migration stops the deploy before the backend is replaced. The job deletes the rendered files from the runner's workspace whatever the outcome. Re-running an earlier deploy run rolls the server back to its SHA; across a migration it needs an `alembic downgrade` first (README, Deployment). README, Deployment, lists the secrets.
