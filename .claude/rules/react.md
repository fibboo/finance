# React Rules

These rules apply to new and changed code under `frontend/`, together with `.claude/rules/typescript.md`.

## Stack

The frontend is a responsive, mobile-first single-page app. It is built from React 19 with the React Compiler, Vite and React Router 8 in data mode. TanStack Query 5 holds server state, and forms use React Hook Form with Zod 4. The API client is `openapi-fetch`, typed by `openapi-typescript` from the backend's OpenAPI schema. Styling is CSS Modules over CSS custom-property tokens. Tests run with Vitest, Testing Library, user-event and MSW. Every call goes to `/api`, which the dev server and the production web server proxy to the backend (`.claude/skills/add-module/SKILL.md`). A new library is added only when a current issue needs what none of these provide.

## Structure

- `frontend/src/app/` holds the router, the providers, the query client and the root error boundary.
- `frontend/src/features/<feature>/` holds one domain (`accounts`, `transactions`, `auth`) in `api/`, `components/`, `hooks/` and `schemas/` subfolders. A feature never imports from another feature. Routes in `app/` compose features, and shared code moves down into a shared folder once a second feature needs it.
- `frontend/src/components/` holds shared UI with no domain knowledge. `frontend/src/lib/` holds the configured API client and other library setup, and `frontend/src/styles/` holds the tokens and global styles.
- The generated API types live in `frontend/src/lib/api-schema.ts`, are regenerated by a `package.json` script from the backend's `/openapi.json` and are committed. CI fails when the committed file is stale. It is generated code: ESLint and Prettier ignore it in their configs, and no rule of this file or of `.claude/rules/typescript.md` applies to it.

## Components

- Function components only, one exported component per file, named like the file in PascalCase (`account-list.tsx` exports `AccountList`).
- Components and hooks are pure. Rendering never mutates props, state, refs or module variables, and gives the same output for the same input. The React Compiler depends on this.
- Props are a `type` named `<Component>Props`, `readonly`, destructured in the signature.
- Composition over prop drilling: pass `children` or an element prop instead of threading data through layers that do not use it. Context is for app-wide values that rarely change (the auth session, the theme), never for server data or state that changes often. The dictionaries are server data and are read through their query hook.
- A list item's `key` is the entity's id, never the array index.
- No component is defined inside another component.
- A component stays small enough to read in one screen. When it renders more than one concern, each concern becomes its own component, following the flat structure of `.claude/rules/common.md`: the parent composes and the children do not orchestrate.

## Hooks and Effects

- Hooks are called at the top level only (`react-hooks` rules), and a custom hook is named `use<Thing>` in a `use-<thing>.ts` file.
- An effect only synchronizes with a system outside React (a browser API, a subscription, a non-React widget). It never derives data, fetches data, handles an event or resets state. Derived values are computed during render, event logic goes in the handler, and state is reset by changing the component's `key`.
- No `useMemo`, `useCallback` or `memo` by default; the React Compiler memoizes. One is added only when a profile shows the need or an effect dependency must keep its identity, and the PR says which.
- A lint rule of `react-hooks` is never suppressed. Code the Compiler cannot handle is rewritten.

## State

- Server data lives only in TanStack Query. It is never copied into `useState`, Context or a store. The one exception is a form's starting values: an edit form passes the entity from its query into React Hook Form's `values`, and the form owns the edited copy until it is submitted.
- UI state lives in the component that owns it and is lifted only as far as the nearest common parent. No global state library is added until a current issue needs one.
- State holds the minimum. Anything that can be computed from props, other state or query data is computed during render.
- The URL holds what should survive a reload or be shareable: filters, page, the selected entity. It is read and written through React Router's search params.

## Data Fetching

- Every query is declared once with `queryOptions` in the feature's `api/` folder, in a key factory per entity (`accountQueries.list(params)`, `accountQueries.detail(id)`). Components, loaders and invalidations use the factory, never a hand-written key.
- A query key runs from general to specific and contains every value the fetcher uses.
- Every request goes through TanStack Query, except the token refresh and the session restore of the API client's auth middleware (**Auth and Security**).
- Fetchers are plain functions over the one `openapi-fetch` client in `frontend/src/lib/`. The client turns an error response into an `ApiError` and throws it.
- Route loaders only prefetch, with `queryClient.ensureQueryData`. Components read with `useQuery` or `useSuspenseQuery`, so the query cache stays the one source of server data.
- A mutation invalidates the affected keys through the factory prefix in `onSuccess` and returns that promise, so its pending state lasts until the fresh data has arrived. An optimistic update uses TanStack Query's mutation `variables` or `onMutate`, not `useOptimistic`.
- The query client sets a global `staleTime` and does not retry a 4xx. Errors are reported in one place: the `QueryCache` and `MutationCache` `onError` show a notification, and an error that leaves the screen unusable reaches the route's error boundary.
- The dictionaries of value sets and labels (`.claude/rules/common.md` **Architecture**) are loaded once at startup through queries with an infinite `staleTime`.

## Forms

- Every form uses React Hook Form with `zodResolver` and a Zod schema in the feature's `schemas/` folder. The form's types are inferred from the schema, the input type and the output type separately, and never written by hand.
- Fields are read with `useWatch`, never with `watch()`, which the Compiler cannot track.
- Submitting calls a TanStack Query mutation. A 422 from the backend is mapped onto the fields with `setError`, from the field errors the `ApiError` carries.
- React's `useActionState` and form actions are not used, since React Hook Form owns form state.

## Routing

- Routes are declared once in `frontend/src/app/` with `createBrowserRouter`. Every route below the root is loaded with `lazy`.
- Every route has an `ErrorBoundary`, combined with TanStack Query's `QueryErrorResetBoundary` so that a retry refetches.
- A route that needs a signed-in user is wrapped by one layout route that redirects to sign-in. Screens do not check auth themselves.

## Auth and Security

- The access token is kept in memory only. The refresh token is an `HttpOnly`, `Secure`, `SameSite=Strict` cookie that the backend sets on its auth path (`/user/auth`), so script never reads it. The browser sees that path as `/api/user/auth`, so the dev proxy and the production web server rewrite the cookie's `Path` to match (`.claude/skills/add-module/SKILL.md`); the backend knows nothing of the `/api` prefix. Neither token is ever written to `localStorage`, `sessionStorage` or a readable cookie.
- One middleware of the API client adds the access token, refreshes it once on a 401 while sharing a single in-flight refresh between concurrent requests, and signs the user out when the refresh fails. On startup the app restores the session through the same refresh.
- The refresh is shared across browser tabs as well, not only within one tab. Every tab uses the same refresh cookie, and the backend rotates the refresh token with reuse detection. A second tab that presents a token another tab has just rotated revokes the whole token family and signs the user out everywhere. So a refresh takes a Web Locks lock (`navigator.locks.request`) under one name. Once it holds the lock, it first checks whether another tab has already refreshed (the new access token arrives over a `BroadcastChannel`) and calls `/user/auth/token` only if none did.
- Sign-out calls `/user/auth/revoke`, which always succeeds, even without a cookie. When a refresh fails, the backend clears the cookie itself.
- No `dangerouslySetInnerHTML`. A URL from data is checked to be `http:` or `https:` before it goes into an `href` or `src`.
- A response from the backend is not parsed again: its contract is the generated types (`.claude/rules/common.md` **Security**). Data from anywhere else (the URL, storage, a third party) is parsed with Zod before use.

## Styling

- Each component that needs styles has one colocated `<file>.module.css`. Class names are camelCase.
- Colors, spacing, radii, font sizes and breakpoints are CSS custom properties in `frontend/src/styles/tokens.css`, with the dark theme overriding the same names. A module uses `var(--token)`, never a raw color, pixel size or font.
- Styles are mobile-first: base rules for the smallest screen, then `min-width` media or container queries. Sizes use `rem`. Touch targets are at least 44 by 44 pixels.
- Mobile-first is the order the styles are written in, not a target that stops at the phone. Every screen is finished for desktop too: wide layouts use the space with columns or a side panel instead of a stretched phone column, text lines keep a readable maximum width, and hover and focus states exist for pointer and keyboard. A screen is checked at a phone width and at a desktop width before its PR is opened.
- Switching between phone and desktop is seamless. Both widths show one app, not two: the same screens and routes, the same navigation sections in the same order, the same names, icons and colors for the same things, and the same actions in the same order of steps. Only the arrangement adapts (a bottom bar becomes a side bar, a list and its detail move from two screens onto one), never what exists or what it is called. A feature never exists at one width only. Both widths render the same components, which reflow with CSS; there are no separate mobile and desktop component trees.
- No inline `style` except for a value computed at runtime, such as a progress width.

## Accessibility

- Semantic HTML first: a `button` for an action, an `a` for navigation, a `label` for every input, and landmarks (`header`, `nav`, `main`). ARIA is added only when no native element expresses the role.
- Everything works with the keyboard alone, with a visible focus state. Focus moves to a dialog when it opens and returns when it closes.
- Images have `alt`. An icon-only button has an accessible name.
- Text and controls meet WCAG 2.2 AA contrast in both themes.

## Tests

- A component test renders the component the way the app does, with a fresh `QueryClient` (`retry: false`), the router and the app's providers. That wrapping lives in one shared `render` in `frontend/src/test/render.tsx`, the counterpart of a `conftest.py` fixture and the one shared test function the suite keeps. MSW's server and its lifecycle live in the Vitest setup file.
- Elements are found as a user finds them: `getByRole` with a `name` first, then `getByLabelText`, then `getByText`. `getByTestId` only when nothing else can find the element. Queries go through `screen`.
- Interaction goes through `userEvent.setup()` and is awaited. `fireEvent` is not used.
- An async result is awaited with `findBy*`.
- The network is mocked with MSW handlers, and the server is started with `onUnhandledRequest: 'error'`. The test asserts what the user sees or what request reached the network, never component state, hook internals, class names or a snapshot of the tree.
- A component that only lays out children, a schema, a key factory or a token file is not the subject of a test (`.claude/rules/python.md` **Tests**: a definition is never the subject of a test). Their behaviour is tested through the screen that uses them.
